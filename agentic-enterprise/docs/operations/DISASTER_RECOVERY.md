# التعافي من الكوارث

## 1. ما يجب حمايته

| المكوّن | الموقع (الإعداد) | الأهمية | يُعاد بناؤه؟ |
|---------|------------------|---------|---------------|
| قاعدة البيانات | `DATABASE_PATH`، مع ملفي `-wal` و`-shm` | حرجة: المهام، والموافقات، والتصعيدات، والذاكرة، وaudit، والمفاتيح العامة | لا |
| ملف تثبيت audit | `AUDIT_ANCHOR_FILE` | حرج: دونه لا يمكن إثبات سلامة audit | لا |
| مفتاح التثبيت | `AUDIT_ANCHOR_KEY` في مدير الأسرار | حرج | لا. فقدانه يعني عدم إمكان التحقق من التثبيتات السابقة |
| المفاتيح الخاصة للموافقين | لدى كل موافق | فقدانها يمنع صاحبها من القرار فقط | نعم: مفتاح جديد عبر `keys init` |
| حالة الـ mocks | `mock-state.json` | تطوير فقط | نعم |

## 2. النسخ الاحتياطي

**المتطلبات:**
- **تكرار:** يومي على الأقل، وقبل أي ترقية.
- **حجم البيانات المقبول فقده (RPO):** 24 ساعة في وضع التجربة، والمستهدف للإنتاج ≤ 15 دقيقة عبر النسخ المتزامن بعد الانتقال إلى PostgreSQL.

**الإجراء المؤتمت (موصى به):**
```bash
npm run ops -- backup --out backup/$(date +%F)                  # منصة واحدة: DATABASE_PATH وAUDIT_ANCHOR_FILE
npm run ops -- backup --out backup/$(date +%F) --data-root ./data   # الخادم: مستوى التحكم وكل مستأجر
npm run ops -- backup verify backup/$(date +%F) [--data-root .]      # يجب أن تكون كل الوحدات OK
```
- اللقطة بواجهة النسخ في SQLite، فهي متسقة أثناء الكتابة.
- التثبيت يُقص عند آخر seq في اللقطة، فيتحقق دون إنذار كاذب.
- `manifest.json` يحمل رأس السلسلة وSHA-256 لكل ملف.
- **التمرين مؤتمت:** `ops/backup.test.ts` يأخذ نسخة أثناء النشاط، ويتحقق منها، ويستعيدها، ويشغل المنصة منها. ويكشف النسخة المعدّلة حتى لو عُدّل الـ manifest أيضًا.

**الإجراء اليدوي (مرجعي):**
```bash
# 1) لقطة متسقة للقاعدة (لا تنسخ الملف مباشرة أثناء الكتابة)
node --disable-warning=ExperimentalWarning -e "
  const {DatabaseSync, backup} = require('node:sqlite');
  const db = new DatabaseSync(process.env.DATABASE_PATH);
  backup(db, process.argv[1]).then(() => console.log('ok'));
" "backup/enterprise-$(date +%F).db"
# 2) ملف التثبيت (append-only): نسخه بعد لقطة القاعدة يضمن أنه يغطيها
cp "$AUDIT_ANCHOR_FILE" "backup/anchor-$(date +%F).jsonl"
```
النسخ تُخزَّن في موقع منفصل، وبالإقامة الإقليمية المطلوبة للعميل (`SAUDI_APPLICABILITY.md`).

## 3. الاستعادة

1. أوقف كل العمليات: `ops kill "restore" --as u-ops`.
2. استبدل `DATABASE_PATH` بالنسخة، واحذف ملفي `-wal` و`-shm` القديمين.
3. **ملف التثبيت:**
   - إن كان الملف الحالي سليمًا ولم يُفقد، **احتفظ به ولا تستبدله**. سيحتوي تثبيتات أحداث أحدث من النسخة، فيعلن التحقق "anchored event missing". هذا متوقع ويوثّق بالضبط ما فُقد.
   - لإعادة التشغيل اعتمد مسار القرار الموثق في الخطوة 5.
4. `ops audit verify` يجب أن ينجح على النسخة مع ملف التثبيت المنسوخ معها.
5. **قرار موثق** من platform_operator وCISO (يُسجَّل في التذكرة):
   - **أ.** بدء ملف تثبيت جديد من النسخة، مع الاحتفاظ بالقديم كدليل، ونقطة بداية جديدة مسجلة في audit.
   - **ب.** أو التحقيق قبل أي تشغيل إن كان سبب الحادث تلاعبًا.
6. المهام التي كانت `running` لحظة النسخ تُستعاد آليًا عند انتهاء إيجارها (ADR-007).
7. الموافقات المعتمدة غير المنفذة تبقى `approved`:
   - راجعها، واسحب (`ops revoke`) ما لم يعد صحيحًا.
   - ثم نفّذ `ops release` و`ops resume`.
8. **التسوية مع الأنظمة الخارجية:**
   - أي دفعة أو أمر شراء نُفّذ بعد وقت النسخة غير موجود في القاعدة المستعادة.
   - **قارن مع البنك وERP يدويًا قبل الاستئناف.** المنصة لا تضمن تنفيذًا لمرة واحدة بالضبط عبر أنظمة خارجية. تضمن عدم التكرار داخلها فقط (nonce وdedupe)، والتسوية مسؤولية بشرية بعد الاستعادة.

## 4. فقدان مفتاح التثبيت

- لا يمكن التحقق من التثبيتات السابقة. السلسلة نفسها ما تزال قابلة للتحقق.
- ولّد مفتاحًا جديدًا، وابدأ ملف تثبيت جديدًا، ووثّق الحادث، وأرشف الملف القديم كدليل.
- **في الإنتاج:** المفتاح في HMS أو KMS مع نسخ احتياطي داخل مدير الأسرار، فهذا السيناريو يجب ألا يحدث.

## 5. تسرب مفتاح موافق خاص

1. `ops keys revoke <humanId> --as u-ops` فورًا. كل توقيع لاحق بالمفتاح يُرفض.
2. راجع القرارات الموقعة بهذا المفتاح، بالبصمة في `ops audit tail` وسجلات الموافقات، منذ آخر وقت كان فيه المفتاح آمنًا.
3. الموافقات المعتمدة غير المنفذة التي وقّعها: اسحبها (`ops revoke`).
4. مفتاح جديد عبر `ops keys init`.

## 6. حالة التحقق

| الإجراء | مختبر؟ |
|---------|--------|
| استعادة المهام العالقة بعد انهيار عامل | ✅ آليًا (`hardening.test.ts`) |
| كشف حذف أو إعادة كتابة بعد الاستعادة | ✅ آليًا (`audit-anchor.test.ts`) |
| النسخ والاستعادة الكاملة بالإجراء أعلاه | ⬜ يدويًا فقط. الأتمتة مخططة (`IMPLEMENTATION_ROADMAP.md`) |

## ملحق: الخادم متعدد المستأجرين وPostgreSQL (2026-10-15)

ما يجب نسخه معًا، في اللحظة نفسها قدر الإمكان:

| المكوّن | SQLite | PostgreSQL |
|---------|--------|------------|
| مستوى التحكم (المستأجرون والرموز وaudit الخاص به) | `DATA_ROOT/control.db` | schema `ae_control` |
| بيانات كل مستأجر | `DATA_ROOT/tenants/<id>/enterprise.db` | schema `ae_t_<id>` |
| تثبيت audit (خارج القاعدة عن قصد) | `DATA_ROOT/control-anchor.jsonl`، و`tenants/<id>/audit-anchor.jsonl` | الملفات نفسها على القرص |
| حالة الأنظمة الوهمية (تطوير فقط) | `tenants/<id>/mock-state.json` | — |

```bash
# PostgreSQL: نسخة لكل مستأجر، تسمح باستعادة مستأجر واحد دون غيره
pg_dump "$DATABASE_URL" --schema=ae_t_acme --format=custom --file=acme-$(date +%F).dump
pg_dump "$DATABASE_URL" --schema=ae_control --format=custom --file=control-$(date +%F).dump
```

**بعد أي استعادة:**
1. `npm run ops -- audit verify` لكل مستأجر، أو `GET /readyz`.
2. **التثبيت أحدث من القاعدة المستعادة** (الحالة الطبيعية بعد الاستعادة): التحقق يُبلغ عن أحداث مثبتة مفقودة. هذا متوقع ويجب توثيقه كحادثة استعادة، لا تجاهله. التثبيت يثبت بالضبط ما فُقد.
3. **الرموز:** تُستعاد مع مستوى التحكم. ما أُلغي بعد لحظة النسخة يعود صالحًا، **فأعد إلغاءه فورًا** من سجل audit لمستوى التحكم (`token.revoke`).

**SQLite:** تمرين الاستعادة مؤتمت (`ops/backup.test.ts`). **PostgreSQL:** النسخ بـ pg_dump يدوي، وتمرين استعادة مؤتمت لم يُبنَ بعد.
